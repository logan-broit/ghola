# pg_recall v0.3 — Contradiction Detection

## Context

The Bayesian confidence system in pg_recall already has the *mechanism* for
handling contradictions. When `bayesian_update(prior, 0.10)` is called, confidence
collapses rapidly — from 0.8 to 0.32 on the first contradiction, to 0.078 on the
second. The evidence constants are well-defined:

```
0.05  user rejected
0.10  contradiction detected
0.50  neutral (no information)
0.65  co-activation reinforcement
0.95  user confirmed
```

What's missing is the *detection*. Nothing in the system today identifies when a
new memory contradicts an existing one. The Bayesian machinery sits idle until
someone manually calls `update_confidence(mneme_id, 0.10)`. This feature closes
that gap.

## The Problem

Contradiction detection in a SQL extension — without an LLM in the loop — faces
a fundamental limitation: **semantic similarity does not imply contradiction**.

Two memories about "Python version" with high cosine similarity could be:
- **Reinforcing:** "Python 3.12 is widely adopted" and "Python 3.12 has great performance"
- **Contradicting:** "Python 3.8 is the latest" and "Python 3.12 is the latest"

Vector distance alone cannot distinguish these cases. The cosine similarity
between both pairs would be high — they share the same topic and similar language.

## Design: Detection + Flagging

Given this limitation, pg_recall takes a **detection + flagging** approach rather
than fully automatic resolution:

1. **Detect candidates** — find existing mnemes that are semantically close to a
   new or updated mneme (high vector similarity, same workspace)
2. **Flag for review** — insert candidates into a `contradiction_candidates` table
   with similarity scores and metadata
3. **Let the caller decide** — the upstream system (e.g., Chapterhouse) reviews
   candidates, possibly using an LLM or user input to confirm actual contradictions
4. **Apply the mechanism** — confirmed contradictions trigger
   `update_confidence(mneme_id, 0.10)` on the contradicted memory, using the
   existing Bayesian machinery

This design keeps pg_recall's role clear: it surfaces *what might contradict*,
not *what does contradict*. The judgment call stays with the caller.

## Detection Strategy

### Candidate Criteria

A contradiction candidate is a pair of mnemes in the same workspace where:

1. **High semantic similarity** — cosine similarity >= configurable threshold
   (default 0.85). This catches memories about the same topic.
2. **Different content** — the `content` fields are not identical (trivially,
   exact duplicates are not contradictions).
3. **Both active** — only `state = 'active'` mnemes are candidates. Dormant and
   archived memories are excluded.
4. **Concept overlap** (optional signal) — same or similar `concept` field
   strengthens the contradiction signal. Two memories labeled "python version"
   are more likely to contradict than two memories that happen to share embedding
   space.

### When to Detect

Detection runs at two points:

1. **On insert** — when a new mneme is stored, check for candidates against
   existing mnemes. This is the primary path.
2. **On demand** — a SQL function that scans for contradiction candidates across
   all active mnemes in a workspace. This is for bulk review.

The on-insert path uses a trigger function that fires `AFTER INSERT` on the
`mnemes` table. This keeps detection automatic without requiring the caller to
remember to check.

## Schema

### Table: `contradiction_candidates`

```sql
CREATE TABLE contradiction_candidates (
    id              bigserial PRIMARY KEY,
    workspace_id    uuid NOT NULL,
    mneme_a         uuid NOT NULL REFERENCES mnemes(id) ON DELETE CASCADE,
    mneme_b         uuid NOT NULL REFERENCES mnemes(id) ON DELETE CASCADE,
    similarity      double precision NOT NULL,
    concept_overlap boolean NOT NULL DEFAULT false,
    status          text NOT NULL DEFAULT 'pending'
        CHECK (status IN ('pending', 'confirmed', 'dismissed')),
    created_at      timestamptz NOT NULL DEFAULT now(),
    resolved_at     timestamptz,
    UNIQUE (mneme_a, mneme_b)
);

CREATE INDEX contradiction_candidates_workspace_idx
    ON contradiction_candidates (workspace_id, status);
```

**Design choices:**

- `mneme_a` is always the newer mneme (the one that triggered detection).
  `mneme_b` is the existing mneme it potentially contradicts.
- `UNIQUE (mneme_a, mneme_b)` prevents duplicate flagging of the same pair.
- `ON DELETE CASCADE` cleans up candidates when either mneme is deleted.
- `status` tracks the lifecycle: `pending` → `confirmed` or `dismissed`.
- `concept_overlap` is true when both mnemes share the same `concept` value,
  providing an additional signal for the reviewer.

## Functions

### `check_contradictions(mneme_id uuid, similarity_threshold float8 DEFAULT 0.85) -> SETOF contradiction_candidate_result`

Checks a specific mneme against all other active mnemes in the same workspace.
Returns candidate pairs above the similarity threshold. Does NOT insert into
the candidates table — this is a read-only query for inspection.

### `flag_contradictions(mneme_id uuid, similarity_threshold float8 DEFAULT 0.85) -> bigint`

Same detection logic as `check_contradictions`, but inserts results into the
`contradiction_candidates` table. Returns the number of candidates flagged.
Skips pairs that are already flagged (respects UNIQUE constraint).

This is what the trigger calls on insert.

### `resolve_contradiction(candidate_id bigint, resolution text) -> text`

Resolves a contradiction candidate. `resolution` must be `'confirmed'` or
`'dismissed'`.

- **confirmed**: applies `bayesian_update(confidence, 0.10)` to the *older*
  mneme (`mneme_b`), reducing its confidence. Sets `status = 'confirmed'` and
  `resolved_at = now()`.
- **dismissed**: sets `status = 'dismissed'` and `resolved_at = now()`. No
  confidence change.

Returns `'ok'`.

### `scan_workspace_contradictions(workspace_id uuid, similarity_threshold float8 DEFAULT 0.85) -> bigint`

Bulk scan: checks all active mnemes in a workspace against each other for
contradiction candidates. Useful for initial setup or periodic review. Returns
the number of new candidates flagged.

This is an expensive operation (O(n^2) comparisons, though HNSW indexing
amortizes the vector search). Should be run infrequently.

### `get_pending_contradictions(workspace_id uuid, limit_n int DEFAULT 50) -> SETOF contradiction_detail`

Returns pending contradiction candidates with full mneme details for review.
Ordered by similarity descending (highest similarity = most likely contradiction).

### Composite Types

```sql
CREATE TYPE contradiction_candidate_result AS (
    candidate_id    bigint,
    mneme_a         uuid,
    mneme_b         uuid,
    similarity      float8,
    concept_overlap boolean
);

CREATE TYPE contradiction_detail AS (
    candidate_id    bigint,
    similarity      float8,
    concept_overlap boolean,
    concept_a       text,
    content_a       text,
    confidence_a    float8,
    concept_b       text,
    content_b       text,
    confidence_b    float8,
    created_at      timestamptz
);
```

## Trigger

```sql
CREATE OR REPLACE FUNCTION contradiction_check_trigger()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    PERFORM pg_recall.flag_contradictions(NEW.id, 0.85);
    RETURN NEW;
END;
$$;

CREATE TRIGGER mneme_contradiction_check
    AFTER INSERT ON mnemes
    FOR EACH ROW
    EXECUTE FUNCTION contradiction_check_trigger();
```

The trigger fires after every insert. The similarity threshold is hardcoded at
0.85 in the trigger but can be overridden by calling `flag_contradictions`
directly.

**Performance consideration:** The trigger runs an HNSW nearest-neighbor search
for every insert. For typical workloads (tens of inserts per minute), this is
negligible. For bulk imports, the trigger can be temporarily disabled.

## Integration with Existing Systems

### Bayesian Confidence Flow

```
New mneme inserted
    │
    ├── trigger fires flag_contradictions()
    │       │
    │       ├── HNSW search for similar active mnemes
    │       │
    │       ├── candidates above threshold → INSERT into contradiction_candidates
    │       │
    │       └── (no automatic confidence change)
    │
    ▼
Caller reviews pending contradictions
    │
    ├── resolve_contradiction(id, 'confirmed')
    │       │
    │       └── bayesian_update(mneme_b.confidence, 0.10)
    │           older mneme's confidence drops
    │
    └── resolve_contradiction(id, 'dismissed')
            │
            └── no confidence change, candidate closed
```

### Hebbian Interaction

Contradiction candidates that are confirmed should also affect the association
graph. When two mnemes are confirmed as contradicting:
- Any existing association between them should have its weight reduced (or the
  association removed)
- Future co-activation of the pair should not reinforce their association

This is deferred to implementation — the simplest approach is to delete the
association on confirmation.

### Worker Integration

The background worker (v0.2) does not process contradiction candidates. Detection
happens synchronously via the insert trigger. Resolution is always caller-driven.

A future enhancement could have the worker periodically run
`scan_workspace_contradictions` for workspaces that haven't been scanned recently,
but this is not part of the initial implementation.

### Test Cases

- Insert two similar mnemes → contradiction candidate flagged
- Insert two dissimilar mnemes → no candidate flagged
- Insert exact duplicate content → no candidate (same content is not contradiction)
- Concept overlap detection (same concept field)
- Resolve as confirmed → older mneme confidence drops
- Resolve as dismissed → no confidence change
- Duplicate flagging prevented (UNIQUE constraint)
- Workspace isolation (different workspaces don't cross-flag)
- Archived/dormant mnemes excluded from detection
- `get_pending_contradictions` returns only pending status
- `scan_workspace_contradictions` finds existing contradictions
- Deleting a mneme cascades to its candidates

## Open Questions

1. **Threshold tuning.** 0.85 cosine similarity is a starting point. Real-world
   testing will determine the right threshold — too low creates noise, too high
   misses contradictions. The threshold is a parameter on all functions, not a
   hardcoded constant.

2. **Concept similarity vs exact match.** The current design uses exact concept
   match for `concept_overlap`. A future enhancement could use fuzzy matching
   or concept embedding similarity.

3. **Bi-directional confidence impact.** Currently, only the older mneme
   (`mneme_b`) gets its confidence reduced on confirmation. Should the newer
   mneme also be affected? The assumption is "newer information is more likely
   correct," but this isn't always true.

4. **Association cleanup.** On confirmed contradiction, should existing Hebbian
   associations between the pair be deleted or just weakened?
