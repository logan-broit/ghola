# pg_ghola v0.2 — Autonomous Background Worker

## Context

v0.1 ships the cognitive memory core: scoring primitives (ACT-R, Ebbinghaus,
Bayesian, softplus), Hebbian association learning via explicit SQL batch
functions, and composite `recall()` fusing vector similarity, full-text search,
temporal activation, and confidence. Co-activation processing is driven manually
through `process_co_activation_batch()` or `process_all_pending_co_activations()`.

v0.2 adds a pgrx background worker that automates co-activation processing, runs
periodic decay/pruning, and exposes live operational stats.

## Chapterhouse Integration

The goal of completing pg_ghola v0.2 is to integrate it into Chapterhouse
(`~/code/chapterhouse`) as the replacement for Qdrant. Key decisions:

- **No backward compatibility required.** `pg_ghola.mnemes` replaces
  Chapterhouse's `memory_blocks` table entirely. Clean migration is acceptable —
  new schema, new tables.
- **No schema hedging.** pg_ghola's data model is the source of truth. The
  Chapterhouse Go code (`internal/vector/qdrant.go`) will be rewritten to call
  `pg_ghola.recall()` via SQL.
- **Integration branch:** `feat/pg-recall-integration` on the Chapterhouse repo.
- **Chapterhouse's CNPG cluster already runs PostgreSQL 18.1** — no PG version
  upgrade needed.

## Configuration

### shared_preload_libraries

v0.2 requires `shared_preload_libraries = 'pg_ghola'` for the background worker.
This is **additive, not breaking** — without it, the extension still installs and
all v0.1 SQL functions work. The background worker simply won't start, and
processing must be done manually (same as v0.1).

### Database GUC

The background worker must connect to the database where `CREATE EXTENSION
pg_ghola` was run. This is configured via a GUC:

```
# postgresql.conf
pg_ghola.database = 'memories'
```

This avoids hardcoding a database name and supports any deployment topology.

## Adaptive Polling State Machine

The worker uses three states with transitions based on queue activity:

```
                  processed > 0
   +--------+  ───────────────>  +--------+
   |  IDLE  |                    | ACTIVE |
   +--------+  <───────────────  +--------+
                no rows for 30s      |
                                     | poll every 100ms
                                     | batch_limit = 100
                 no rows for 5min    |
   +---------+ <─────────────── +--------+
   | DORMANT |                  |  IDLE  |
   +---------+                  +--------+
        |                          poll every 1s
        | poll every 5s
        |
        +── any rows found ──> ACTIVE
```

| State | Poll Interval | Transition Out |
|-------|--------------|----------------|
| Active | 100ms | No rows for 30 consecutive seconds -> Idle |
| Idle | 1s | Processed > 0 -> Active; No rows for 5 minutes -> Dormant |
| Dormant | 5s | Processed > 0 -> Active |

## Periodic Maintenance Jobs

All jobs run inside the worker's main loop. They are checked every poll cycle but
only execute when their interval has elapsed.

### Association Decay (every 1 hour)

```sql
UPDATE pg_ghola.associations
SET weight = weight * 0.999
WHERE updated_at < now() - interval '1 day';
```

Associations not updated in the last 24 hours get a 0.1% weight reduction per
hour. Models natural weakening of unused neural pathways.

### Association Pruning (every 1 hour, after decay)

```sql
DELETE FROM pg_ghola.associations
WHERE weight < 0.001;
```

Associations that have decayed below threshold are removed entirely.

### Dormant Memory Archival (every 6 hours)

```sql
UPDATE pg_ghola.mnemes
SET state = 'dormant'
WHERE state = 'active'
  AND last_access < now() - interval '90 days'
  AND confidence < 0.3;
```

Active memories that haven't been accessed in 90 days with low confidence are
automatically marked dormant. Excluded from `recall()` but not deleted.

## Worker Stats

### Table: `pg_ghola.worker_stats` (singleton row)

```sql
CREATE TABLE worker_stats (
    id                 int PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    state              text NOT NULL DEFAULT 'starting',
    queue_depth        bigint NOT NULL DEFAULT 0,
    batches_processed  bigint NOT NULL DEFAULT 0,
    rows_processed     bigint NOT NULL DEFAULT 0,
    pairs_updated      bigint NOT NULL DEFAULT 0,
    last_batch_at      timestamptz,
    last_decay_at      timestamptz,
    poll_interval_ms   int NOT NULL DEFAULT 100,
    started_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL DEFAULT now()
);
```

### Function: `pg_ghola.get_worker_stats()`

Returns a composite row with worker state and computed uptime. Thin wrapper over
the stats table providing a stable API surface.

## Graceful Shutdown

On SIGTERM, the worker:

1. Stops polling for new work
2. Drains the remaining queue by calling `process_co_activation_batch(100)` in a
   loop until empty or 30-second hard timeout
3. Updates `worker_stats` with state = `'shutdown'`
4. Exits cleanly

## Testing Strategy

### Unit Tests (pure Rust, no Postgres)

In `src/worker.rs`:
- State machine transitions (Active -> Idle -> Dormant timing)
- Polling interval calculations
- Drain timeout behavior

### Integration Tests (pgrx test framework)

In `src/integration_tests.rs`:
- `worker_stats` table exists after `CREATE EXTENSION`
- `get_worker_stats()` function is callable
- Decay SQL correctly reduces association weights
- Pruning SQL removes sub-threshold associations
- Dormant archival SQL transitions correct mnemes

### Manual Smoke Test (documented)

The background worker cannot be automatically tested in pgrx because:
- Tests run in rolled-back transactions; the worker runs in a separate backend
- `shared_preload_libraries` must be set before the test cluster starts
- Timing-dependent behavior is fragile in CI

The worker is intentionally a thin orchestration layer over existing, well-tested
batch functions.

## Success Criteria

v0.2 is successful when:

- `shared_preload_libraries = 'pg_ghola'` starts the background worker on boot
- Co-activation queue is automatically drained without manual SQL calls
- Worker adapts polling interval based on queue activity
- Association decay and pruning run on schedule
- Dormant archival transitions stale low-confidence memories
- `get_worker_stats()` returns live operational data
- Graceful shutdown drains in-flight work
- All v0.1 SQL functions continue to work unchanged
