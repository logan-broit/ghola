# Iteration 9 (2026-04-12, samsara)

**What**: Ablation study -- isolate the relaxed lexical pathway contribution.

**Hypothesis**: The relaxed lexical pathway (added in Iter 8) contributes >5pp R@5
improvement on the Iter 8 pinned database. If removing it drops R@5 by more than the
variance budget (4.2pp), the pathway is valuable and should be kept.

## Method

Disabled the relaxed lexical pathway by forcing `cleaned_query = None` in recall.rs.
This is functionally equivalent to removing the CTE entirely -- the conditional inclusion
logic already handles `None` by emitting empty strings for both the CTE and UNION clauses.

Deployed to cluster, ran 3x retrieve-only benchmark with full retrieval-time state reset
between each run. Compared against Iter 8 baseline (3-run mean, same pinned database).

## Analysis

The relaxed lexical pathway is **harmful**. Removing it improved every metric:

1. **Candidate pool dilution**: The relaxed CTE fires when strict lexical returns zero
   results. But those zero-result queries are zero because the query terms don't match
   content well. The relaxed version (temporal words stripped) finds SOME matches, but
   they're low-quality -- they match on residual content words without the discriminative
   power of the full query. These weak candidates enter the pool and compete with better
   semantic and cluster matches, pushing correct results below the top-k cutoff.

2. **Variance injection**: The relaxed pathway's NOT EXISTS guard makes its firing
   probabilistic -- it depends on whether the strict lexical CTE happens to return ANY
   results. Small changes in the strict lexical results (from Hebbian drift or
   co-activation ordering) toggle the relaxed pathway on/off, creating a cascading
   variance source. Removing it produces 5x tighter variance (0.8pp vs 4.2pp spread).

3. **Neuroscience reinterpretation**: The pathway was motivated by Tulving's encoding
   specificity principle (1972) -- temporal framing words in queries but not in content
   block the @@ filter. However, the correct interpretation is that encoding specificity
   means retrieval cues must match the ENCODING context. Stripping temporal words from
   the query creates an asymmetric match that doesn't reflect how the memory was encoded.
   The right fix is at encoding time (add temporal context to the tsvector), not at
   retrieval time (strip temporal context from the query).

## Decision

**Permanently removed** the relaxed lexical pathway code:
- Removed `strip_temporal_stop_words()` function and `TEMPORAL_STOP_WORDS` constant
- Removed relaxed_lexical CTE generation and SQL template placeholders
- Removed associated pg_test and unit tests (8 tests removed, 26 remaining)

## Key constraints discovered

- **Relaxed lexical pathway is harmful**: Dilutes candidate pool with weak matches,
  injects variance via probabilistic NOT EXISTS guard. All categories improve without it.
- **Retrieval-time temporal word stripping is wrong direction**: Encoding specificity
  means fixing the ENCODING (add temporal context to tsvector), not the QUERY.
- **Candidate pool purity matters**: Fewer, higher-quality candidates beat more,
  lower-quality ones. Guard against pool dilution in future pathway additions.

## What to try next

1. **Multi-granularity encoding** (high impact, high effort): Extract per-turn or per-fact
   sub-mnemes during gating. Helps single-session-user, multi-session, temporal simultaneously.
   Requires schema changes + embedding generation at gating time.

2. **Temporal retrieval pathway** (moderate effort): Use content_dates column in a new CTE.
   Many temporal-reasoning queries include date cues not leveraged today.

3. **Encoding-time temporal enrichment**: Add temporal context (dates, relative time markers)
   to the tsvector during gating, so the strict lexical pathway can match temporal queries
   naturally. This is the correct application of encoding specificity.
