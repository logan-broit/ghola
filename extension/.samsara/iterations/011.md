# Iteration 11 (2026-04-12, samsara)

**What**: Query decomposition for multi-event retrieval + temporal pathway analysis

**Hypothesis**: (A) A dedicated temporal CTE matching query dates against content_dates would
improve temporal-reasoning R@5. (B) Decomposing multi-event queries ("between X and Y") into
per-event FTS sub-queries would improve candidate generation for temporal-reasoning and
multi-session categories.

**Result**: REVERTED. Both hypotheses invalidated.
- Hypothesis A: 0/133 temporal queries contain explicit dates. content_dates is unpopulated
  (1/18917 mnemes). Date-matching pathway has zero opportunity.
- Hypothesis B: Query decomposition is indistinguishable from noise. Benchmark variance
  (~17pp spread) completely dominates any signal from the change.

## Neuroscience Grounding

Cue decomposition (Tulving, 1983): complex retrieval cues decomposed into simpler cues
that match individual memory encodings. The hypothesis was that multi-event queries like
"How many days between visiting MoMA and the Ancient Civilizations exhibit?" fail
AND-conjunction FTS because terms span two sessions. Per-event sub-queries would match
individual sessions.

However, the practical application fails because:
1. The benchmark's temporal queries use relative time references (77%), not explicit dates
2. The decomposition adds candidates but their effect is masked by extreme benchmark variance

### Query decomposition analysis
- Multi-event queries (2+ sub-queries): 133/500 (27%)
  - temporal-reasoning: 51/133 (38%)
  - single-session-assistant: 36/56 (64%)
  - multi-session: 33/133 (25%)
- Single-event queries (1 sub-query): 367/500 (73%)
  - Single sub-queries are relaxed lexical matches, which are harmful (iter 9 constraint)

### Implementation
1. `decompose_query()`: Splits queries on connectors ("between...and", "and", "or", comma),
   strips temporal framing words, keeps segments with 2+ content words.
2. `split_on_connectors()`: Handles "between X and Y" structure, then splits on "and"/"or".
3. Per-event FTS CTEs: Each sub-query gets its own CTE with AND-conjunction FTS,
   UNION ALL'd into the candidate pool.
4. Multi-event gate: Only decompose when 2+ sub-queries exist (single sub-query = relaxed
   lexical, known harmful).
5. DISTINCT ON ordering: Added `ORDER BY id, fts_rank DESC` to ensure highest fts_rank
   survives deduplication across CTEs.

## Key Constraints Discovered

- **0/133 temporal queries contain explicit dates**: Temporal queries use relative time
  ("ago", "between", "before") not dates. Date-matching retrieval pathways have zero
  opportunity on this benchmark.
- **content_dates unpopulated**: Only 1/18917 mnemes has content_dates populated. The
  `extract_dates()` YYYY/MM/DD fix from iter 10 is in the code but the pinned database
  predates the fix. Must re-run gating or update via migration.
- **Single sub-queries are relaxed lexical**: Query decomposition that produces 1 sub-query
  is just frame-word stripping, equivalent to the harmful relaxed lexical pathway (iter 9).
  Must gate on 2+ sub-queries.
- **DISTINCT ON dedup is non-deterministic**: When multiple CTEs compute different fts_rank
  for the same mneme, DISTINCT ON picks arbitrarily. Fix: add ORDER BY id, fts_rank DESC.
- **Bimodal benchmark variance**: First run after pod restart consistently LOW, second run
  HIGH. Likely cause: HNSW index/shared_buffers warmup. The first run loads index pages
  into PostgreSQL's shared buffer cache; the second run hits cached pages.
  Spread: 6-17pp. This dominates any code-change signal.
- **Consolidation worker processes co-activation during benchmark**: At 100ms poll interval,
  the worker creates hebbian associations in near-real-time during the run. These accumulate
  and affect queries later in the same run.
- **Sentence-transformers embedding server has higher variance**: Compared to iter 9
  baseline (2.2pp with TEI), the sentence-transformers server shows 6-17pp variance.

## What to Try Next

1. **Fix benchmark variance** (critical): The 6-17pp bimodal variance makes code changes
   unmeasurable. Options:
   a. Always discard the first run after pod restart (warmup run)
   b. Pre-warm HNSW index before benchmarking (run a few queries, discard results)
   c. Restore the original TEI/vLLM embedding server for lower variance
   d. Pin shared_buffers configuration to ensure index is cached

2. **Populate content_dates via migration** (moderate effort): Run a SQL migration using
   the fixed `extract_dates()` to populate content_dates for all mnemes. This enables
   future temporal pathways if query-side date extraction improves.

3. **Multi-granularity encoding** (high impact, high effort): Per-turn or per-fact sub-mnemes
   during gating. This addresses the root cause of diluted session-level embeddings.
