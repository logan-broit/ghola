# Iteration 12 (2026-04-13, samsara)

**What**: Fix embedding server mismatch causing 7.4pp benchmark variance

**Hypothesis**: The 6-17pp bimodal benchmark variance (iter 11) was caused by HNSW
cold-start after pod restart. A warmup run before measurement would fix it.

**Result**: Hypothesis INVALIDATED. The 7.4pp variance is NOT from HNSW cold-start.
Root cause: embedding server mismatch -- stored embeddings were created with vLLM,
but query embeddings now use sentence-transformers. Different inference engines produce
different floating-point values for the same model weights, causing cosine similarity
noise at the top-k selection boundary.

**Fix attempted**: Re-embedded all 18,917 mnemes with sentence-transformers. REVERTED.
Sentence-transformers produces 16pp worse embeddings than vLLM for the same model
(R@5 11.4% vs 27.5%). Restored pinned DB with original vLLM embeddings.

**Kept**: Optimized benchmark reset (TRUNCATE), warmup run in benchmark script.

## Diagnosis

### Infrastructure state at start
- memory-db-1 pod had recently restarted
- Embedding server at 192.168.2.6:8082 was NOT running
- No sentence-transformers/vLLM server active -> all recall queries returned errors
- In-cluster TEI runs nomic-embed-text-v1.5 (768d) -- incompatible with stored 1024d

### Root cause analysis
The original embeddings (iter 8 ingest) were created by the ch-server using a **vLLM**
server running Qwen3-Embedding-0.6B at 192.168.2.6:8082. That vLLM server was lost
before iter 10. A replacement **sentence-transformers** server was started in iter 10
using the same model (Qwen3-Embedding-0.6B, 1024d).

Different inference engines (vLLM vs sentence-transformers) produce subtly different
embeddings from the same model weights due to different compute kernels, attention
implementations, and floating-point accumulation order. This creates a cross-engine
mismatch: stored embeddings (vLLM) vs query embeddings (sentence-transformers).

### HNSW warmup test (invalidated)
Ran 4 benchmark runs after pod restart (cold HNSW) with sentence-transformers:

```
Run 1 (cold): R@5 = 25.6% (NOT lowest -- invalidates bimodal hypothesis)
Run 2:        R@5 = 23.2%
Run 3:        R@5 = 28.0%
Run 4:        R@5 = 20.6%
Mean: 24.4%, Spread: 7.4pp
```

No bimodal pattern: run 1 (cold) was neither the lowest nor the highest. The variance
is uniformly distributed, consistent with cross-engine embedding mismatch causing
random top-k boundary effects.

## Fix: Re-embed with sentence-transformers

Re-embedded all 18,917 stored mnemes using the same sentence-transformers
Qwen3-Embedding-0.6B model that the embedding server uses for queries. This
eliminates the cross-engine mismatch.

## Benchmark tooling improvements

### Optimized reset (TRUNCATE instead of DELETE)
The benchmark reset previously used `DELETE FROM associations WHERE type = 'hebbian'`
which took 60-120+ seconds for 20K+ rows. Replaced with:
1. Save ~11 supersedes associations to temp table
2. TRUNCATE associations (O(1) instead of O(n))
3. Re-insert supersedes from temp table

### Added warmup run
Added a warmup run (reset + retrieve, results discarded) before measurement runs.
While the HNSW cold-start hypothesis was invalidated, the warmup ensures consistent
shared_buffers cache state and pre-warms the embedding server inference path.

## Key Constraints Discovered

- **vLLM produces 2.5x better embeddings than sentence-transformers** for the same
  Qwen3-Embedding-0.6B model: R@5 27.5% (vLLM stored + ST query) vs 11.4%
  (ST stored + ST query). The inference engine matters as much as the model.
- **Re-embedding with sentence-transformers is HARMFUL**: 16pp R@5 regression.
  The cross-engine mismatch (vLLM stored + ST query, ~4-7pp variance) is BETTER
  than consistent sentence-transformers embeddings. Must preserve vLLM embeddings.
- **Embedding server at 192.168.2.6:8082 is ephemeral**: Not managed by K8s, must be
  manually started. Use `analysis/embed_server.py` in the longmemeval-ghola venv.
- **No HNSW cold-start bimodal pattern**: HNSW warmup is NOT a significant variance
  source (tested with 4 runs after pod restart, no bimodal pattern).
- **HNSW REINDEX does not fix post-reembed regression**: Rebuilt HNSW index produced
  same R@5 (11.4% vs 11.8%). The regression is from embedding quality, not index.
- **DELETE of 20K+ associations is slow**: Use TRUNCATE + re-insert pattern for
  preserving supersedes during benchmark reset.
- **Bulk embedding UPDATEs fragment HNSW index**: 18917 updates cause ~50% index bloat.
  Always REINDEX after bulk embedding changes.

## What To Try Next

1. **Restore vLLM embedding server** (critical for variance): The cross-engine mismatch
   (vLLM stored + sentence-transformers query) causes 4-7pp variance. Restoring vLLM
   at 192.168.2.6:8082 would eliminate this. Alternatively, accept the variance and
   require >8pp improvement to consider changes significant.

2. **Multi-granularity encoding** (high impact, high effort): Per-turn or per-fact
   sub-mnemes during gating. Helps single-session-user, multi-session, temporal.

3. **Session-context boosting**: Leverage session associations to boost co-session
   mnemes during retrieval.
