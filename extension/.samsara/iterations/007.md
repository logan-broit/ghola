# Iteration 7 (2026-04-11, samsara)

**What**: Fix benchmark methodology -- pin embeddings via database dump, reset ALL retrieval-time
state between runs, measure run-to-run variance.

**Hypothesis**: By pinning the database (COPY binary dumps of a single ingest) and resetting
ALL retrieval-time state (access_count, co_activation_queue, AND hebbian associations) before
each retrieve-only run, we can make benchmark comparisons reliable for future iterations.
This blocked ALL further code changes (STATE.md priority 0).

## Discoveries

### 1. Bench tag mismatch caused 0% retrieve-only results

When `run.py all` was run during Iter 6, it generated a random workspace UUID (`855c3273-...`),
producing bench tag `bench_855c3273`. The MCP server mapped this workspace to the canonical
`00000000-0000-0000-0000-000000000001`. But when `run.py retrieve --workspace-id 00000000-...`
was run, it computed bench tag `bench_00000000`, which matched zero mnemes. All 500 queries
returned "No matching memories found" from the MCP recall tool.

**Fix**: Updated all 19,181 mneme tags from `bench_855c3273` to `bench_00000000` in the database.
This makes the standard workspace ID work for all future retrieve-only runs.

**Root cause**: `run.py all` uses `str(uuid.uuid4())` when no `--workspace-id` is provided,
but `run.py retrieve` needs the SAME workspace ID to generate the matching bench tag. The MCP
server's workspace ID mapping is transparent -- the bench tag is the actual scoping mechanism.

### 2. Hebbian associations are the primary source of run-to-run degradation

Initial runs with only access_count + co_activation_queue reset showed a degrading trend:
- Run 1: R@5 = 9.8%, Run 2: 6.4%, Run 3: 5.0% (clear downward trend)
- 200K+ hebbian associations accumulated across runs, creating rich-get-richer drift

Once hebbian associations were included in the reset (DELETE WHERE association_type = 'hebbian'),
the trend disappeared and variance stabilized:
- Clean Run 1: R@5 = 9.0%, Run 2: 10.0%, Run 3: 11.2% (no degrading trend)
- Mean: 10.1%, Spread: 2.2pp

## Implementation

### Database fixes
- Updated bench tags: `array_replace(tags, 'bench_855c3273', 'bench_00000000')` on all 19,181 mnemes
- Full retrieval-time state reset: access_count=1, last_access=created_at, DELETE hebbian
  associations, TRUNCATE co_activation_queue

### Scripts created
- `analysis/benchmark_reset.sh` -- full retrieval-time state reset (access_count + associations + queue)
- `analysis/benchmark_run.sh` -- orchestrates N retrieve-only runs with reset between each
- `analysis/benchmark_restore.sh` -- restore pinned database from binary COPY dumps
- `analysis/variance_report.py` -- analyze variance across multiple benchmark runs

## Key constraints discovered

- **Bench tag mismatch**: `run.py all` (random UUID) vs `run.py retrieve --workspace-id` (fixed UUID)
  generates different bench tags, causing 0% results. Must always use workspace_id
  `00000000-0000-0000-0000-000000000001` for retrieve-only runs.
- **Hebbian associations cause degrading trend**: Without clearing hebbian associations,
  successive runs degrade (9.8% -> 6.4% -> 5.0%). The rich-get-richer effect compounds.
- **Full reset eliminates degrading trend**: Clearing access_count + associations + queue
  stabilizes variance to 2.2pp spread across 3 runs.
- **pg_dump cannot export extension-member tables**: Tables created by CREATE EXTENSION
  are excluded from pg_dump data dumps. Use COPY binary format instead.
- **Iter 6 ingest has different embedding quality than Iter 2**: R@5 ~10% vs 29.2%.
  TEI CPU float32 non-determinism produces different embeddings per ingest.
