# Iteration 16 (2026-04-18, samsara)

**What**: Multi-granularity encoding -- per-turn sub_mnemes with isolated
embedding per turn, replacing session-level encoding as the retrieval primitive.

**Hypothesis**: The current 27.5% R@5 (Iter 9 matched baseline) is bottlenecked
by encoding granularity, not retrieval scoring or embedding model. A session-
level embedding is a lossy average of 10+ turns; a query about a specific fact
in turn 3 can't match an embedding that averages turns 0-N. Storing one
embedding per turn (sub_mnemes) and searching at that granularity should close
a meaningful slice of the gap toward BM25 (~70%) and pgvector (34.6%).

Encoding choice: isolated per-turn via Qwen3-Embedding-0.6B's native last-token
pooling. Decision record: commits `a39fac5`, `cbf71eb`, `4d74450`, `e2b9880`
in the chapterhouse / pg_ghola repos showed late-chunking's best variant caps
at +11pp of an ~60pp gap while hurting self-contained content by -20pp.
Isolated encoding is simpler, has no regression modes, and unlocks the
cognitive primitives to do the longitudinal differentiation work (which was
never going to happen on a cold benchmark anyway).

Target: >35% R@5 overall (>7.5pp gain on iter 9's 27.5% baseline). Variance
budget: >2pp to be significant.

## Infrastructure Change

### pg_ghola v0.0.6 image

Extension schema (src/schema.rs, src/recall.rs, src/types.rs):
  - New `ghola.sub_mnemes` table: per-turn rows linked to parent mneme via FK
    cascade. Columns: id, mneme_id (FK), position (0-indexed smallint), role,
    content, embedding vector(1024), search_vector (generated tsvector from
    content), token_start, token_end (char offsets), created_at.
  - HNSW index on sub_mnemes.embedding, GIN index on search_vector, btree on
    (mneme_id, position). HNSW becomes the new hot path for semantic retrieval.
  - Composite type `ghola.recall_result` gains a ninth field,
    `matched_position smallint`. `recall_inner` function signature updated to
    return 9 columns. `recall` SQL wrapper constructs 9-tuples.
  - Recall CTEs rewritten: semantic / lexical pathways now search sub_mnemes
    with DISTINCT ON (mneme_id) to pick best sub_mneme per parent; entity /
    cluster pathways unchanged (continue to operate on parent mnemes). Legacy
    mnemes without sub_mnemes fall through via semantic_legacy / lexical_legacy
    CTEs guarded by `NOT EXISTS (SELECT 1 FROM sub_mnemes ...)`.

Phase 1 committed in pg_ghola at `80e120f`. Docker image built locally as
`cnpg-pg18-ghola:18.1-ghola-0.0.6` (748MB) via the existing single-base
Dockerfile.cnpg pattern (CNPG base for both builder and runtime, pgvector
rebuilt with `OPTFLAGS="-march=x86-64-v2"` per the iter 4 war story).

### ch-server ghola-v3 image

Chapterhouse Go changes (committed 6efa6c3, f21c347):
  - `Store.RememberWithTurns(ctx, ...)` writes one parent mneme plus N
    sub_mnemes atomically via pgxpool transaction. Turn content is the raw
    LongMemEval turn text formatted as
    `"[timestamp: X] [session: Y] [role]: content"`.
  - Embedding: one batched `provider.Embed([turn0, turn1, ...])` call per
    ingest (max batch 32; LongMemEval-S median 12 turns fits in a single HTTP
    round-trip to `embed_server.py` on `:8082`).
  - New MCP tool `remember_session` with nested turns schema, dispatched to
    `handleRememberSession` which parses char offsets by cumulative running
    length and delegates to `RememberWithTurns`.

Built as `ch-server:ghola-v3` (50MB, Alpine).

### The permission-denied trap

First benchmark attempt failed at every `insert_sub_mneme`:
```
ERROR: permission denied for table sub_mnemes (SQLSTATE 42501)
```

Root cause: the prior `pg_ghola.mnemes` table was granted to the `memory_api`
role during CNPG bootstrap (via `postInitSQL`'s `CREATE EXTENSION pg_ghola`
and pgrx-generated grants). The new `sub_mnemes` table, added via raw SQL
migration instead of extension UPDATE, did not inherit those grants.

Fix: added `GRANT SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
ON TABLE ghola.sub_mnemes TO memory_api;` to the end of the migration SQL
(commit `1e56b83`). Applied ad-hoc to the live cluster, then cleaned up the
partial-ingest benchmark rows via
`DELETE FROM ghola.mnemes WHERE tags && ARRAY['bench_<id>']`.

Constraint captured for future migrations: any new table created via raw SQL
outside of pgrx's ALTER EXTENSION UPDATE path must explicitly grant privileges
to application roles. pgrx handles this automatically during CREATE EXTENSION
but not during post-install additive schema.

## Key Constraints Discovered

- **Post-install schema additions require explicit GRANT**: pgrx hands out
  grants to the application role during `CREATE EXTENSION`. Tables added
  later via raw SQL migration inherit none of that. Any future iter-N
  migration that adds tables or sequences must include the grant statements
  or debug the same "permission denied" error in production.

- **CNPG rollovers are fast enough to not need staged deploys**: the
  single-instance memory-db-1 pod rolled over in ~4 min with imagePullPolicy:
  Never. ch-server rolled over in ~30s. The total "migration window" where
  recall queries could fail (new binary, old catalog) was bounded by the
  migration SQL runtime (~2 seconds). In practice, dropping + recreating
  the function/type while the pod is Ready with the new binary is a narrow
  enough window that deliberate ch-server scale-down wasn't strictly needed
  (though it's still recommended for safety).

- **ArgoCD's selfHeal reverts manual kubectl scaling**: attempting to
  `kubectl scale deployment ch-server --replicas=0` manually was reverted
  within 30-60s by ArgoCD's selfHeal. The right knob for production deploys
  is to either (a) put the scale change in git and push, or (b) disable
  auto-sync on the application temporarily via `argocd app set --sync-policy
  none`. Option (a) is GitOps-native; option (b) requires remembering to
  re-enable it.

- **Extension symlink stays at pg_recall in production**: the cluster
  installed the extension as `pg_recall` (not `pg_ghola`) via the
  Dockerfile's symlink trick. ALTER EXTENSION and AS '$libdir/...' paths
  in the migration SQL must reference `pg_recall`, not `pg_ghola`.
  Documented in the migration file comment.
