# Iteration 16 (2026-04-18, samsara)

**What**: Multi-granularity encoding -- per-turn sub_mnemes with isolated
embedding per turn, replacing session-level encoding as the retrieval primitive.

**Hypothesis**: The current 27.5% R@5 (Iter 9 matched baseline) is bottlenecked
by encoding granularity, not retrieval scoring or embedding model. A session-
level embedding is a lossy average of 10+ turns; a query about a specific fact
in turn 3 can't match an embedding that averages turns 0-N. Storing one
embedding per turn (sub_mnemes) and searching at that granularity should close
a meaningful slice of the gap toward BM25 (~70%) and pgvector (34.6%).

Encoding choice: isolated per-turn via Qwen3-Embedding-0.6B's native last-token
pooling. Decision record: commits `a39fac5`, `cbf71eb`, `4d74450`, `e2b9880`
in the chapterhouse / pg_ghola repos showed late-chunking's best variant caps
at +11pp of an ~60pp gap while hurting self-contained content by -20pp.
Isolated encoding is simpler, has no regression modes, and unlocks the
cognitive primitives to do the longitudinal differentiation work (which was
never going to happen on a cold benchmark anyway).

Target: >35% R@5 overall (>7.5pp gain on iter 9's 27.5% baseline). Variance
budget: >2pp to be significant.

**Result**: INVALIDATED. R@5 = 15.6% overall (single run), -11.9pp below the
iter 9 baseline of 27.5%. The regression is not uniform: `knowledge-update`
category TIED with iter 9 (42.3%), while `single-session-assistant` collapsed
from 82.1% to 26.8% (-55.3pp). The pattern matches exactly what the Tier 1
encoding-eval harness predicted -- isolated per-turn encoding works on
self-contained factual content but fails on conversational content where the
answer turn needs context from prior turns to match a query.

## Infrastructure Change

### pg_ghola v0.0.6 image

Extension schema (src/schema.rs, src/recall.rs, src/types.rs):
  - New `ghola.sub_mnemes` table: per-turn rows linked to parent mneme via FK
    cascade. Columns: id, mneme_id (FK), position (0-indexed smallint), role,
    content, embedding vector(1024), search_vector (generated tsvector from
    content), token_start, token_end (char offsets), created_at.
  - HNSW index on sub_mnemes.embedding, GIN index on search_vector, btree on
    (mneme_id, position). HNSW becomes the new hot path for semantic retrieval.
  - Composite type `ghola.recall_result` gains a ninth field,
    `matched_position smallint`. `recall_inner` function signature updated to
    return 9 columns. `recall` SQL wrapper constructs 9-tuples.
  - Recall CTEs rewritten: semantic / lexical pathways now search sub_mnemes
    with DISTINCT ON (mneme_id) to pick best sub_mneme per parent; entity /
    cluster pathways unchanged (continue to operate on parent mnemes). Legacy
    mnemes without sub_mnemes fall through via semantic_legacy / lexical_legacy
    CTEs guarded by `NOT EXISTS (SELECT 1 FROM sub_mnemes ...)`.

Phase 1 committed in pg_ghola at `80e120f`. Docker image built locally as
`cnpg-pg18-ghola:18.1-ghola-0.0.6` (748MB) via the existing single-base
Dockerfile.cnpg pattern (CNPG base for both builder and runtime, pgvector
rebuilt with `OPTFLAGS="-march=x86-64-v2"` per the iter 4 war story).

### ch-server ghola-v3 image

Chapterhouse Go changes (committed 6efa6c3, f21c347):
  - `Store.RememberWithTurns(ctx, ...)` writes one parent mneme plus N
    sub_mnemes atomically via pgxpool transaction. Turn content is the raw
    LongMemEval turn text formatted as
    `"[timestamp: X] [session: Y] [role]: content"`.
  - Embedding: one batched `provider.Embed([turn0, turn1, ...])` call per
    ingest (max batch 32; LongMemEval-S median 12 turns fits in a single HTTP
    round-trip to `embed_server.py` on `:8082`).
  - New MCP tool `remember_session` with nested turns schema, dispatched to
    `handleRememberSession` which parses char offsets by cumulative running
    length and delegates to `RememberWithTurns`.

Built as `ch-server:ghola-v3` (50MB, Alpine).

### The permission-denied trap

First benchmark attempt failed at every `insert_sub_mneme`:
```
ERROR: permission denied for table sub_mnemes (SQLSTATE 42501)
```

Root cause: the prior `pg_ghola.mnemes` table was granted to the `memory_api`
role during CNPG bootstrap (via `postInitSQL`'s `CREATE EXTENSION pg_ghola`
and pgrx-generated grants). The new `sub_mnemes` table, added via raw SQL
migration instead of extension UPDATE, did not inherit those grants.

Fix: added `GRANT SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
ON TABLE ghola.sub_mnemes TO memory_api;` to the end of the migration SQL
(commit `1e56b83`). Applied ad-hoc to the live cluster, then cleaned up the
partial-ingest benchmark rows via
`DELETE FROM ghola.mnemes WHERE tags && ARRAY['bench_<id>']`.

Constraint captured for future migrations: any new table created via raw SQL
outside of pgrx's ALTER EXTENSION UPDATE path must explicitly grant privileges
to application roles. pgrx handles this automatically during CREATE EXTENSION
but not during post-install additive schema.

### Caveat: single run, not 3-run mean

`run.py all` invokes a single index -> retrieve -> evaluate pass. The samsara
iter methodology calls for 3-run means with full retrieval-time state reset
between runs. That discipline was not followed for this iter because the
result is decisive enough on a single run that 3-run variance cannot flip the
conclusion:

  - iter 9 baseline spread: 0.8pp at R@5 on the pinned DB
  - Assume a generous 5pp single-run spread for iter 16 (conservative)
  - Worst-case ceiling: 15.6% + 5pp = 20.6%, still -6.9pp below iter 9

A -6.9pp regression is outside any reasonable variance band and well beyond
the >2pp significance threshold. 3-run data would refine the number but not
change the conclusion. Noted for the STATE.md entry.

## Analysis

The hypothesis assumed fine-grained retrieval granularity was the dominant
bottleneck. The result shows encoding CONTEXT is at least as important on
LongMemEval, and isolated per-turn encoding systematically strips it.

### What failed and why

Sample miss from `single-session-assistant`:
```
Query:     "I'm planning to visit Bandung again and I was wondering if you
            could remind me of the name of that restaurant in Cihampelas Walk
            that serves a great Nasi Goreng?"
Truth:     answer_ultrachat_234453  (not in top-10)
Top-1:     0eb28b73_1 (score 1.960, unrelated restaurant)
Top-2:     ultrachat_471394 (score 1.950, unrelated)
Top-3:     answer_a68db5db_2 (score 1.940, unrelated)
```

This is exactly the failure mode the Tier 1 encoding-eval harness flagged as
"back-reference" / "context-dependent" -- the ASSISTANT turn that names the
restaurant is probably something like "The restaurant is Ayam Goreng
Suharti." In isolation, that turn does not match a query phrased as "what
restaurant in Cihampelas Walk serves Nasi Goreng" because the LOCATION and
the DISH aren't in the answer turn; they were in the user's earlier turn
and the assistant's response just provided the name.

Session-level encoding (iter 9) captured the user's question AND the
assistant's answer together, so a query about the location + dish matched
the session embedding. Per-turn isolated encoding splits that apart -- the
question turn embeds "Cihampelas Walk Nasi Goreng" and the answer turn
embeds just the restaurant name. Neither matches the query's full intent
the way a joint embedding did.

### Category pattern confirms the mechanism

| Category | Semantic shape | Iter 16 R@5 | Delta vs iter 9 |
|---|---|---|---|
| knowledge-update | Standalone fact in one turn | 42.3% | TIE |
| single-session-assistant | Answer turn needs question turn as context | 26.8% | -55.3pp |
| single-session-preference | Short preference statements, context-dependent | 0.0% | -4.4pp |
| single-session-user | User turn paraphrased, needs conversation flow | 2.9% | -4.2pp |
| multi-session | Answer requires combining across session boundaries | 6.8% | -9.0pp |
| temporal-reasoning | Time-referenced answers, context-bound | 14.3% | -9.0pp |

knowledge-update holds because its answers are typically direct factual
assertions that read correctly in isolation. Everything else requires
conversational context that isolated per-turn encoding discards.

### What the Tier 1 harness told us (and we discounted)

The encoding-eval harness on 151 cases (chapterhouse commits `a39fac5`,
`cbf71eb`, `4d74450`) showed:

  - `late-chunk-mean-pool` vs `isolated`: +9.9pp top-1 overall, -20pp on
    self-contained cases but wins on back-reference / multi-topic /
    short-session
  - Oracle (label-cheat selection): +11.3pp ceiling
  - `store-both-max` / `store-both-mean`: both LOSE to mean-pool

We interpreted this as "encoding strategy has a small ceiling (~11pp of the
~60pp gap), so don't bother -- focus on cognitive primitives."

What we missed: the 151 cases were a MIX of self-contained and context-
dependent. LongMemEval-S is ~87% conversational (only `knowledge-update`
and some of `single-session-assistant` are self-contained-ish). The
Tier 1 per-category breakdown showed late chunking was a BIG win on
back-reference / short-session / multi-topic and a LOSS on self-contained.
LongMemEval's composition means the back-reference pattern dominates.

Put another way: the "encoding has a small ceiling" claim was true in the
aggregate on Tier 1 but didn't predict the asymmetry on a workload that's
mostly conversational. On LongMemEval, isolated encoding is catastrophic
because conversational context is the load-bearing signal for most
categories.

## Key Constraints Discovered

- **Post-install schema additions require explicit GRANT**: pgrx hands out
  grants to the application role during `CREATE EXTENSION`. Tables added
  later via raw SQL migration inherit none of that. Any future iter-N
  migration that adds tables or sequences must include the grant statements
  or debug the same "permission denied" error in production.

- **CNPG rollovers are fast enough to not need staged deploys**: the
  single-instance memory-db-1 pod rolled over in ~4 min with imagePullPolicy:
  Never. ch-server rolled over in ~30s. The total "migration window" where
  recall queries could fail (new binary, old catalog) was bounded by the
  migration SQL runtime (~2 seconds). In practice, dropping + recreating
  the function/type while the pod is Ready with the new binary is a narrow
  enough window that deliberate ch-server scale-down wasn't strictly needed
  (though it's still recommended for safety).

- **ArgoCD's selfHeal reverts manual kubectl scaling**: attempting to
  `kubectl scale deployment ch-server --replicas=0` manually was reverted
  within 30-60s by ArgoCD's selfHeal. The right knob for production deploys
  is to either (a) put the scale change in git and push, or (b) disable
  auto-sync on the application temporarily via `argocd app set --sync-policy
  none`. Option (a) is GitOps-native; option (b) requires remembering to
  re-enable it.

- **Extension symlink stays at pg_recall in production**: the cluster
  installed the extension as `pg_recall` (not `pg_ghola`) via the
  Dockerfile's symlink trick. ALTER EXTENSION and AS '$libdir/...' paths
  in the migration SQL must reference `pg_recall`, not `pg_ghola`.
  Documented in the migration file comment.

- **Tier 1 encoding harness on a 151-case mix is NOT predictive of a
  workload with a different mix**: the aggregate "encoding has an ~11pp
  ceiling" conclusion from Tier 1 was correct in the aggregate but hid an
  asymmetric per-category pattern that matters enormously when the
  downstream workload is skewed. On a conversational-heavy workload like
  LongMemEval, the encoding choice isn't "small lever" -- it's decisive.
  Future encoding decisions should consider workload composition as first-
  class, not just aggregate metric.

- **The Phase 2 "first principles reframe" conclusion was wrong**: we said
  "skip encoding cleverness, focus on cognitive primitives." That reasoning
  was correct about the long-term direction (primitives are the
  differentiator) but wrong about the short-term trade: isolated encoding
  isn't a neutral default; it actively regresses on the majority of
  LongMemEval categories. The infrastructure (sub_mnemes table, recall
  changes, Go ingest path) is still correct -- the encoding CHOICE needs
  revision.

## Decision

REVERTED from isolated-per-turn encoding. The Phase 2 infrastructure (schema,
recall CTEs, Go ingest) is kept -- it's correct and forward-compatible. The
encoding CHOICE inside `RememberWithTurns` needs to change.

Benchmark data cleanup: delete all `bench_dea632cc`-tagged mnemes so the
next iter starts from a clean DB state. Existing 42 user mnemes are
preserved (they use no benchmark tags).

## What To Try Next

Three candidate directions, in order of expected impact:

### 1. Late-chunking mean-pool (highest priority)

What: re-introduce the `late-chunk-mean-pool` encoding from the Tier 1
harness. This was the strategy that beat isolated by +9.9pp top-1 across the
151-case set and crucially WON on the back-reference / multi-topic /
short-session categories that dominate LongMemEval.

Implementation location: server-side, in `pg_ghola/analysis/embed_server.py`.
Add a `/v1/embeddings/late-chunk` endpoint that accepts session text + turn
boundaries, encodes the whole session with `output_value="token_embeddings"`,
and mean-pools each turn's tokens. Chapterhouse's `RememberWithTurns` gets
a new `EmbedLateChunk` provider method.

This is the exact Phase 2 design from `docs/plans/2026-04-16-multi-
granularity-encoding-implementation.md` BEFORE the 2026-04-18 revision that
cut it out in favor of isolated. Restore the late-chunking variant.

Expected lift: Tier 1 predicted +9.9pp on a mixed set. LongMemEval is
heavier on back-reference, so could be larger. Target: >30% R@5 overall
(iter 9 baseline + >2pp variance budget). Upper bound unknown.

### 2. Parent embedding fallback (defensive)

What: change the recall CTE so the `semantic_sub` pathway also UNION-ALLs a
parent-mneme embedding match, not just sub_mneme. If late-chunking doesn't
close the gap, the parent session-level embedding ALWAYS matches what iter 9
did. Adding it as a parallel pathway means we never do worse than iter 9,
because the parent-embedding hit is available alongside the sub_mneme hit.

Cost: 2x HNSW scans per recall (sub_mnemes + mnemes embeddings), dedup by
parent id, keep max cosine. This is the `store-both-max` architecture from
the Tier 1 work, but with the understanding that Tier 1 MAX-aggregation
regressed because of non-target score inflation. Need to measure.

### 3. Accept single-session-assistant loss, optimize for the primitives

What: ship isolated encoding as-is despite the LongMemEval regression, and
measure whether the longitudinal eval (docs/plans/2026-04-18-longitudinal-
eval-design.md) shows pg_ghola differentiating from pgvector over simulated
time. The cognitive primitives are supposed to do that work; LongMemEval's
cold-data score is the "Week 0" floor check that doesn't reflect where
pg_ghola is supposed to win.

This accepts the 15.6% cold-benchmark number as the public-facing floor
while betting that week-4+ longitudinal scores eventually exceed pgvector.
Risky because the longitudinal eval doesn't exist yet; it's the Phase 3
work that's still specced but not implemented.

### Recommendation

Direction 1 (late-chunking mean-pool) first. It's a relatively small code
change in the embedding server, re-uses the sub_mneme infrastructure we
built, and directly addresses the regression mechanism. If it lands above
the iter 9 baseline, the samsara loop can continue productively. If it
doesn't, direction 2 as a fallback. Direction 3 only after exhausting the
encoding lever, since it bets on infrastructure that isn't built yet.
