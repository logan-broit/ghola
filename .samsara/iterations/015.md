**What**: Restore vLLM embedding server to eliminate cross-engine embedding mismatch

**Hypothesis**: The 10pp baseline drift (27.5% -> 17.8% R@5) is caused by cross-engine
embedding mismatch: stored embeddings were created with vLLM, but query embeddings use
sentence-transformers. Restoring vLLM for query-time embeddings should recover the baseline
to ~27.5% and reduce variance from 4-7pp back to ~0.8pp.

**Result**: INVALIDATED. vLLM 0.19.1.dev6 produces DIFFERENT embeddings than the original
vLLM that created the stored embeddings. Mean R@5 = 14.9% (3pp WORSE than sentence-
transformers at 17.8%). The original vLLM version/config is irrecoverable. REVERTED to
sentence-transformers.

## Analysis

The vLLM 0.19.1.dev6 Docker image produces embeddings that are EVEN MORE mismatched
with the stored embeddings than sentence-transformers. Several factors contribute:

1. **bfloat16 dtype**: vLLM 0.19.1 defaults to bfloat16. The original vLLM may have used
   float16 or float32. bfloat16 has 8 exponent bits but only 7 mantissa bits (vs 10 for
   float16), losing precision in the embedding values.

2. **Different attention implementation**: vLLM 0.19.1 uses FlashAttention v2 with CUDA
   graph compilation. The original vLLM (unknown version) likely had a different attention
   backend, producing different accumulation patterns.

3. **Pooling configuration**: vLLM 0.19.1 uses `seq_pooling_type='LAST'` (last token
   pooling) with `use_activation=True`. If the original used mean pooling or different
   activation, the embeddings would diverge significantly.

4. **trust_remote_code=False**: vLLM 0.19.1 loaded the model without trust_remote_code,
   which may bypass custom embedding extraction code in the Qwen3-Embedding model.

## Key Constraints Discovered

- **Different vLLM versions produce incompatible embeddings**: vLLM 0.19.1.dev6 is 3pp
  WORSE than sentence-transformers for matching stored vLLM embeddings. Cross-version
  mismatch is as harmful as cross-engine mismatch.

- **The original vLLM embedding engine is irrecoverable**: Without knowing the exact
  vLLM version, dtype, pooling config, and attention backend used during the Iter 8
  ingest, no replacement can reproduce the original embeddings.

- **Embedding server matching requires engine+version pinning**: The Iter 7 DB dump pins
  the stored embeddings but not the engine that created them. Future DB dumps must record
  the exact embedding engine version and configuration.

- **Re-ingest is now the only path to stable matched embeddings**: Neither sentence-
  transformers (17.8%) nor vLLM 0.19.1 (14.9%) can approach the matched baseline (27.5%).
  A fresh ingest with the current engine would create matched embeddings.

## Decision

REVERTED to sentence-transformers. It produces 3pp better results (17.8% vs 14.9%) and
is the known quantity. The vLLM Docker container was stopped and removed.
