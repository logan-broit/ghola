# Iteration 6 (2026-04-11, samsara)

**What**: Additive relaxed lexical fallback pathway. Added a 5th retrieval pathway as a
new CTE (`relaxed_lexical`) that uses temporal stop-word-stripped query for the FTS `@@`
filter, fires ONLY when the strict lexical CTE returns zero results (`NOT EXISTS`).
Code reverted after benchmark showed regression, but investigation revealed the regression
was caused by embedding non-determinism on re-ingest, not the code change itself.

**Hypothesis**: Same as Iter 5 (encoding specificity, Tulving 1972), but with a safe
implementation: a SEPARATE additive CTE that never modifies existing pathway behavior.
The `NOT EXISTS (SELECT 1 FROM lexical)` condition ensures the fallback fires only when
the strict AND filter blocks ALL results, avoiding the displacement mechanism from Iter 5.

**Implementation**:
- Added `strip_temporal_stop_words()` function (17 stop words, case-insensitive)
- Returns None when no temporal words found or <2 content words remain
- Added `relaxed_lexical` CTE: uses cleaned query for `@@` filter, original for `ts_rank`
- Conditional inclusion (like entity_cte): only added to SQL when cleaned query exists
- 6 unit tests, all passing (30/30 total)
- EXPLAIN ANALYZE confirmed: CTE is a complete no-op when lexical has results
  (relaxed_lexical bitmap scan shows "never executed", sub-ms overhead)

**Root cause investigation** (benchmark non-determinism):
1. Reverted code, deployed baseline, ran retrieve-only on SAME database: R@5 = 19.8%.
   Both runs are far below the Iter 2 baseline (29.2%).
2. Jaccard similarity of top-5 session sets: Iter2-Iter5 = 0.853, Iter2-MyRun = 0.325,
   Iter5-MyRun = 0.332. My run retrieves a fundamentally different set of sessions.
3. "Noise attractor" sessions (e.g., `sharegpt_qLEszEA_235`, a trivial "Hello" session)
   appear in 74/500 queries in my run vs 0/500 in baseline. These consume top-k slots
   and push answer sessions out.
4. TEI (text-embeddings-inference, CPU float32, nomic-embed-text-v1.5) produces
   different embeddings for the same text on re-ingest, likely due to CPU floating-point
   non-determinism (thread scheduling, SIMD instruction ordering).
5. The ch-server and TEI pods were not restarted between Iter 5 and my run. Same model,
   same code, same infrastructure. The only difference is a new ingestion run.
6. EXPLAIN ANALYZE confirmed my code change is a complete no-op for queries where the
   strict lexical returns results (which is the vast majority). The relaxed_lexical
   bitmap scan is "never executed" and the NOT EXISTS short-circuits in sub-ms.

**Key discovery: benchmark is non-deterministic on re-ingest**. Full pipeline runs
(truncate + re-ingest) produce different embedding sets due to CPU float32 non-determinism
in TEI. This makes cross-ingest R@k comparisons unreliable. Jaccard overlap between
two ingests on identical infrastructure drops from 0.85 (same ingest) to 0.33 (different
ingest). The 29.2% baseline from Iter 2 is NOT guaranteed reproducible.

**Methodological implications**:
1. **Retrieve-only comparisons** (same database, different code) are reliable but
   confounded by co-activation drift (~478/500 queries differ after 500 co-activation events).
2. **Full pipeline comparisons** (different databases) are unreliable due to embedding
   non-determinism. Iter 2-5 were lucky to have consistent embeddings (same ingest).
3. Future iterations should: (a) use retrieve-only comparisons, (b) reset co-activation
   state between runs, or (c) pin embeddings by importing from a reference database dump.

**Reverted**: Yes -- code reverted, baseline redeployed. Cannot prove the additive pathway
helps because the benchmark comparison is unreliable on this database.

**Next**: Before any further code changes, the benchmark methodology must be fixed:
1. **Pin embeddings**: Create a reference database dump with known-good embeddings.
   Import this dump instead of re-ingesting to eliminate embedding non-determinism.
2. **Reset co-activation**: Truncate co_activation_queue and reset access_count/last_access
   between retrieve-only comparison runs.
3. **Multi-run averaging**: Run retrieve 3x and average R@k to smooth co-activation noise.
