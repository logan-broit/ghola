# Iteration 14 (2026-04-13, samsara)

**What**: Enable dead cluster pathway via startup clustering

**Hypothesis**: The cluster pathway (cortical column voting, Hawkins et al. 2024) is
completely dead -- 0/18917 mnemes have cluster assignments, 0 centroids exist. The
consolidation worker has a 1-hour delay before initial clustering check, so freshly
restored databases never get clusters before benchmarks run.

Fix: fire clustering check at startup. Expected k = sqrt(18917/10) = ~43 clusters,
~440 members each. The cluster pathway searches the 3 nearest clusters (~1320 mnemes)
and picks the top 30 by cosine similarity. This surfaces gold mnemes that are
semantically close to the query but pushed out of the global semantic top-30 by
competitors from other clusters.

This is purely additive (UNION ALL with other pathways). Same scoring formula. Same
variance characteristics as the semantic pathway (no FTS changes that would amplify
embedding mismatch).

**Result**: HARMFUL. Cluster pathway causes ~8pp R@5 regression (17.8% -> 9.7%).
The pathway injects false positive candidates with decent cosine similarity that
displace gold mnemes in scoring. REVERTED.

## Code Change

One-line fix in `consolidation_worker.rs`:
```rust
// Before: wait 1 hour before first clustering check
let mut last_clustering_check = Instant::now();

// After: fire immediately at startup
let mut last_clustering_check = Instant::now() - CLUSTERING_CHECK_INTERVAL;
```

K-means on 18906 x 1024-dim vectors with k=43, max 100 iterations took ~19 minutes

which makes linfa's k-means extremely slow. In production, this should be optimized
or moved out-of-band.

Cluster distribution: 43 clusters, sizes ranging 400-1023 members (mean ~440).

## Analysis: Why Clusters Are Harmful

The cluster pathway adds candidates from the 3 nearest clusters (~1320 mnemes, top 30
by cosine similarity). These candidates have decent cosine similarity (they're from
semantically nearby clusters) but are NOT the gold answers. Combined with FTS saturation
(constant 0.305 for all candidates), the scoring formula cannot differentiate gold from
non-gold cluster candidates:

Effective scoring: `content_match = 0.6 * cosine + 0.305` (FTS constant)

When the semantic pathway returns 30 candidates and the cluster pathway adds 30 more,
the pool doubles. Many cluster candidates have cosine >= 0.85 (close enough to be in
a nearby cluster) while gold mnemes might have cosine ~0.87-0.90. The 0.02 cosine
difference translates to 0.012 score difference -- negligible margin that's easily
overcome by noise. The gold mnemes get displaced by cluster false positives.

### Root cause chain:
1. FTS saturation (iter 2 concept enrichment) -> scoring is 95% cosine-based
2. Cluster candidates have high cosine (from nearby clusters) -> competitive with gold
3. Pool expansion -> more false positives competing for top-K slots
4. Gold mnemes pushed out of top-K by near-miss cluster candidates

### Performance impact:
- Query latency increased ~40% (328s -> 460s) due to additional vector searches
- Clustering itself took 19 min in dev profile (unacceptable for production)

## Key Constraints Discovered

- **Cluster pathway dilutes candidate pool**: Adding candidates from nearby clusters
  is harmful when FTS scoring is saturated. The additional candidates have competitive
  cosine similarity but are not the gold answers. Pool purity > pool size.

- **FTS saturation makes pool expansion universally harmful**: Any pathway that adds
  more candidates without a non-cosine differentiator will regress. Fix FTS first.

- **Cluster pathway needs filtering, not just proximity**: The current implementation
  finds the 3 nearest clusters and picks the top-30 by cosine. This is basically a
  coarser version of the semantic pathway. To be useful, clusters need a DIFFERENT
  signal: intra-cluster diversity, cluster-level FTS, or session-based clustering.

- **K-means in dev profile is 10-20x too slow**: 19 min for 19K vectors. Need release
  profile or an external clustering service. Compilation profile affects k-means
  dramatically (no SIMD vectorization in debug mode).

- **Baseline drift**: Current pod measures 17.8% R@5 without clusters, vs historical
  27.5%. The ~10pp gap is consistent with the cross-engine embedding mismatch (vLLM
  stored embeddings vs sentence-transformers query embeddings). The embedding server
  problem is getting worse, not better.

## What's Changed From Baseline

The historical baseline (27.5%) may no longer be reproducible on the current deployment.
The ablation run (17.8%) establishes a new *observed* baseline. Future iterations should
compare against this 17.8% until the embedding server is fixed.

## What To Try Next

1. **Fix FTS saturation** (HIGHEST PRIORITY): FTS adds constant 0.305 to all candidates,
   making scoring 95% cosine-based. Any pool expansion is harmful until FTS provides
   real differentiation. Approaches:
   - Reduce concept field weight so ts_rank doesn't saturate
   - Use phraseto_tsquery or websearch_to_tsquery for tighter FTS matching
   - Weight FTS by field (title/concept vs content)

2. **Fix embedding server mismatch** (CRITICAL): 10pp baseline drift. Either restore
   vLLM or re-embed with the same engine used for query embeddings.

3. **Multi-granularity encoding** (encoding-time, variance-resistant): Per-turn or
   per-fact sub-mnemes. Changes WHAT is stored, not how scored. Addresses root cause.
